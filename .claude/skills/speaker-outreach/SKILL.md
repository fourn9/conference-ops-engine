# 登壇者アプローチ

## パラメータ

このスキルはメソッドコールとして機能する。呼び出し時に以下を指定：

| パラメータ | 説明 | 例 |
|---|---|---|
| TARGET | 対象者の名前・X/Twitter URL・所属など既知情報 | 「[候補者名] / [公開プロフィール] / CTO at ACME」 |
| EVENT | 対象イベント | 「[イベント名]（[開催日]）」 |
| PHASE | 現在のフェーズ | `research` / `invite` / `follow-up` / `contract` / `thanks` |
| CONTEXT | 追加情報・特記事項（任意） | 「先週RAG批判記事を投稿」「共通の知人：運営責任者経由」 |

未指定の場合は実行前に確認する。

---

## フェーズ別の動作概要

| PHASE | 動作 |
|---|---|
| `research` | diarize-person スキルで候補者プロフィールを作成する |
| `invite` | 調査結果を踏まえて初回招待文を作成する |
| `follow-up` | 前回連絡からの経過時間・返信有無に応じてトーンを調整して文面を作成 |
| `contract` | 契約・旅費・当日詳細の確認メール（金額は人間が記入） |
| `thanks` | 具体的なエピソードを含む感謝メール |

---

## Step 1: 候補者プロフィールの作成（diarization）

**招待文を書く前に必ずこのステップを実行する。読まずに書かない。**

### Step 1a: local/vault 確認（必須）

Obsidian MCP で `01-research/people/` を `search_files`（対象者名）で検索：
- 既存プロフィールあり・`updated` 30日以内 → そのまま使用（Step 2へ）
- 既存プロフィールあり・鮮度低 → 差分調査だけ実施（Step 1b 軽量版）
- 既存プロフィールなし → Step 1b へ

### Step 1b: diarize-person 実行

`diarize-person` スキルを呼び出す：
- NAME: TARGET の名前
- SOURCES: X/Twitter、ブログ、登壇履歴、Notion既存ページ
- PURPOSE: 招待検討

完了後、プロフィールを local/vault `01-research/people/{YYYY-MM-DD}_{名前}.md` に保存（テンプレート: `templates/speaker-profile-template.md`）。

収集・判断する項目：
1. **今この人が一番主張していること**（直近6ヶ月のX・ブログから）
2. **この人が批判・否定していること**（競合思想・業界の問題）
3. **過去登壇のレベル感**（技術深度・規模・スタイル）
4. **現在の所属・役職**（転職・昇進の可能性を公開情報で確認）
5. **主催者との既存接点**（過去連絡・共通知人・メンバーとのX上でのやり取り）

## Step 2: イベントと候補者の接点を言語化

「なぜこの人をこのイベントに招くのか」を1-2行で言えない場合、招待文を書かない。

### イベントごとの接点判断

`conference/event.md` の対象者・開催目的と、候補者の一次情報を照合する。
候補者が実際に扱った課題、設計判断、その経験を必要とする対象者を具体的に書く。
不明な参加人数や実績、相手との関係性を補わない。

---

## Step 3: 招待文の作成

### 構成の原則

```
件名：[候補者の関心テーマ] × [イベント名] のセッションご相談

[名前]様

[1行目：具体的な接点。どの記事・発信を読んだかを明示]

[2-3行：なぜこのイベントでこの人の話を聞きたいか。聴衆への価値]

[2-3行：イベント概要（日時・規模・実績は1-2個に絞る）]

[1行：依頼と次のステップ。返答の期限または形式を明示]

[署名]
```

### 接点文：良い例 vs 悪い例

✅ 良い例：
> 「先週の『RAGはまだ設計問題が解決されていない』というX上の投稿と、
> 続くスレッドの議論を読みました。弊社イベントの参加者（LLMを実装するエンジニア中心）が
> まさに同じ壁にぶつかっており、実装レベルで何が問題かをお話しいただけると
> 非常に価値があると考えています。」

❌ 悪い例：
> 「[候補者名]様の素晴らしいご活躍を常々拝見しております。
> ぜひ弊社の人気カンファレンスにご登壇いただければ幸いに存じます。」

### 本文の長さ

- 日本語：400-500字（件名含まず）
- 英語：200-250 words
- 詳細はPDF資料で補足。本文に数字を詰め込まない

### 英語招待時の追加ルール

- 1文目から用件に入る（日本式の前置き不要）
- 旅費・滞在サポートの範囲を明示（海外からの場合は特に重要）
- 返答期限を具体的に（"If you're interested, could you let us know by June 1?"）
- 候補者の著作・発信から具体的な引用を1箇所以上

## Step 4: フォローアップの判断基準

| 状況 | 対応 |
|---|---|
| 送信後7日以上返信なし | 件名変えず1行のリマインド「ご検討状況をお伺いできますでしょうか」 |
| 送信後14日以上返信なし | 別ルートを検討（共通知人・LinkedIn・X DM）。メール再送はしない |
| 「今回は見送り」の返信 | 理由を一言聞く。「次回のイベントでご相談できますか」と次につなぐ |
| 「興味あり、詳細を」の返信 | 資料送付 + 日程調整を即日実施 |
| 返答なしで2回無視 | 6ヶ月以上間を空ける。強引なフォローは関係を損なう |

---

## Step 5: Notion ページ更新

- 連絡履歴に `[日付] [PHASE] [内容の要点]` を追記
- ステータス更新：`未連絡 / 打診中 / 返信待ち / 承諾 / 辞退 / 検討中`
- `replace_content` を使用（`update_content` より安定）
- 更新後に差分を確認してユーザーに提示
- local/vault `01-research/people/{名前}.md` の `contact_status` フロントマターも同期更新
- Vaultノート末尾の「## ステータスログ」セクションに `[日付]: [内容]` を追記

## よくある失敗パターン

| 失敗 | 原因 | 対策 |
|---|---|---|
| 件名で読まれない | 「カンファレンスご登壇のお願い」のような汎用件名 | 候補者の関心テーマを件名に入れる |
| 内容不一致で断られる | 調査なしで送った | 必ずStep 1の調査を先に行う |
| 返信が来ない | 次のアクションが不明確 | 「〇〇日までに」と期限を書く |
| 関係者に驚かれる | 他の登壇者情報を漏らした | 「著名な実務家の方々」などに留める |
| 所属が違う | 古い情報で送信した | 送信前に公開情報で現職を確認 |

---

## 安全装置

- 送信は行わない（下書き作成まで）
- 契約金額・旅費の具体額は推測で記入しない
- 承諾済みの他登壇者リストはユーザーの明示指示なしに書かない
- 連絡先（メールアドレス・電話番号）は推測で書かない
- 所属・役職は必ず公開情報から確認する

接続先・保存先の共通設定は `docs/configuration.md` を参照。既にユーザーが明示した条件は再確認せず、その範囲で進める。
