# speaker-prospectus（趣意書作成）

## 目的

特別登壇者が確定した後、その人向けの**趣意書**（登壇依頼ドキュメント）を Google Doc で作成する。
**Claude Code との対話で「この人で行く」と決まった、その選定議論の中身（接点・なぜこの人・差別化点・聞きたいこと）を趣意書に織り込む**のが肝。リサーチノートの素材だけでなく、会話で言語化された判断を一次の素材として使う。

## いつ使うか（明示呼び出し）

```
Claude Code と対話 → 候補を議論 → ユーザーが「この人で行く」と決定
                                          ↓ ここで /speaker-prospectus
                          議論で出た選定理由を織り込んで趣意書を生成
```

- **登壇者が確定してから**、`/speaker-prospectus`（または「speaker-prospectus で趣意書を作って」）で明示的に呼ぶ
- 候補検討そのものは別工程（リサーチ／`diarize-person`）。本スキルは**確定後の依頼ドキュメント生成**専用
- 自動発火しない（`disable-model-invocation: true`）。外部の共有 Google Doc を作る操作のため、明示呼び出し＋実行前確認とする

## 前提（入力）

1. **登壇者**：氏名・所属（正式名）・対応テーマ（例 `2-5`）
2. **選定議論の結論**（この会話で出たもの）：接点（どう見つけた／紹介・面識の有無）／なぜこの方か（当事者性の根拠・差別化点・規模インパクト）／当日とくに伺いたい論点
   - ここが「議論を織り込む」中核。会話に無ければユーザーに確認する
3. **テンプレ Doc**：`YOUR_TEMPLATE_DOC_ID`（`利用者が用意する趣意書テンプレート`）
   - タイトル行 `株式会社〇〇 〇〇様` ＋ 5 セクションの `〇〇`。背景・概要・スケジュールは利用者自身のイベント情報から準備する
4. **リサーチノート**：`local/vault/conference/` の該当テーマ研究ファイル（引用記事・当事者性の裏取り素材）

## 手順

### 1. 素材を集める（read-only）

- **会話から**：直前の議論で出た接点・選定理由・聞きたい論点を箇条で抜き出す（最優先素材）
- **本人が話している動画から**（あれば最優先）：具体的な症状・数字・率直な自己評価は、ブログより動画に現れることがある。ユーザーが動画を指定した場合は、内容を依頼理由の軸にする
- **リサーチノートから**：対象者の節を引く
  ```bash
  cd local/vault
  grep -n "<氏名>" conference/*speakers*<theme>*.md
  ```
  取るもの：対応小テーマ／引用記事／当事者性の根拠（役割・実装・運用）／魅力プロキシ
- **テーマ構造から**：`conference/01-planning/session-themes.md` の該当中テーマの最優先小テーマ・課題・主対象職種

### 2. 5 セクションを起草する

| key | 見出し | 中身 |
|---|---|---|
| `participants` | ご参加者について | 視聴ターゲット（企業規模＋職種を具体名で） |
| `challenges` | ご参加者が直面している課題 | テーマの未解決（誰が・何を、が固まっていない） |
| `theme` | 登壇テーマイメージ | タイトル案＋論点3つ |
| `background` | ご登壇依頼とご依頼背景 | **議論で出た接点＋なぜこの方か**（役割で裏取り） |
| `points` | ご相談（具体的に伺いたい論点） | **議論で出た聞きたい論点** |

#### `theme` のタイトル案を設計する

タイトルは、企業の成果を飾るために作らない。参加者がその企業の経験から得る判断の手がかりを、企業が公開できる範囲で短く示す。

次の順序でタイトル案を作る。

1. `challenges` から、参加者が今直面する課題を1つ選ぶ。
2. その課題に対して、登壇企業だけが語れる経験または意思決定を特定する。
3. 参加者が持ち帰る問いまたは判断軸を定める。
4. 企業が実際に話せる範囲を確認し、タイトル案にする。

作成時は、次を確認する。

- 「何をやった会社か」ではなく、「その経験から何を聞けるか」が伝わる。
- 企業の成果紹介で終わらず、参加者が自社に持ち帰れる問いまたは判断軸がある。
- 公開済みの数字、規模、取り組みは、具体性が必要な場合に使う。
- 「成功事例」「最前線」「舞台裏」「徹底解説」など、他社にも使える抽象的または煽り的な表現を使わない。

タイトルで未公開情報の開示を期待させない。公開情報で確認できない限り、失敗の原因、見送った判断基準、社内対立、意思決定の内幕を断定しない。「本音」「裏側」「失敗談」も使わない。

参加者として深く聞きたい論点は `points` に書く。タイトルでは、その論点を企業が無理なく話せる抽象度まで上げる。趣意書で示した「なぜこの企業に依頼するか」の核心を、タイトル案に短く表す。

**書き方の原則（必読）**：
- `background` / `points` は**会話の選定議論をそのまま反映**する。リサーチノートの定型文に逃げない
- 当事者性は**役割で裏取りして進行形で書く**。根拠記事が「解説」主体なら「実装し切った」と**断定しない**
- **本人の内心を代弁しない**。書けるのは本人が公開した事実と、主催者が期待することまで
- **煽りのコピーや運営の内部事情を本人向け文書に載せない**。本人がまだ同意していない主張や、運営の都合は削る
- **数字は算用数字**にし、依頼の結びは「幸いです」を基本とする
- **参照資料は題名・媒体・年月・URLを具体的に示す**。題名は一次情報から取り、宛先本人に関する資料だけを載せる
- **一次情報は本人が語った具体を優先する**。既出の登壇内容がある場合は、それを踏まえて今回何を上乗せしたいかを書く
- **持ち帰りは `theme` に書く**。答えが1つに定まらないテーマでは、単一の正解ではなく判断の手がかりとして示す
- **対談企画では形式と、なぜこの組み合わせで対談するのかを明示する**。相手が未確定なら、その事実も記す
- 平文・要点ファースト・**過剰敬語を避ける**。箇条は行頭 `・`、改行で段落が分かれる
- **AIっぽい文章の癖を避ける**（これが標準フォーマット）。かぎ括弧（「」）を強調目的で使わない、ダッシュ（—／――）や矢印（→）で文をつながない、体言止めを重ねない、三つ並べの対句に頼らない、コロン（：）で文を継がない。強調は語の選び方で出し、文は述語で締める
- 箇条書きは content では行頭 `・` で書けばよい。スクリプトが Google Docs の**ネイティブ箇条書き**に自動変換する（「・」文字は残さない）

content を JSON で用意：
```bash
cat > /tmp/prospectus_content.json <<'JSON'
{
  "participants": "……",
  "challenges": "・……\n・……",
  "theme": "タイトル案は、……です。\n・……\n・……",
  "background": "貴社……を拝読しました。\n……まさに進めている当事者で……。",
  "points": "・……\n・……"
}
JSON
```

### 3. テンプレ複製＋書き込み（fill_prospectus.py が自動でやる）

```bash
cd .claude/skills/speaker-prospectus
# dry-run（コピーも書き込みもしない）
python3 fill_prospectus.py --from-template YOUR_TEMPLATE_DOC_ID \
  --company "サンプル株式会社" --name "サンプル太郎" --content /tmp/prospectus_content.json
# 実行：テンプレ複製 → 氏名/所属＋5空欄を埋める → 検証 → URL 表示
python3 fill_prospectus.py --from-template YOUR_TEMPLATE_DOC_ID \
  --company "サンプル株式会社" --name "サンプル太郎" --content /tmp/prospectus_content.json --apply
```

スクリプトがやること：
1. Drive API でテンプレを複製（ファイル名 `<所属> <氏名>様＿特別ご登壇依頼`、`--title` で上書き可）
2. 本文5空欄を index ベースで丸ごと置換（末尾から適用＝ずれ防止）
3. 本文中の「・」始まり段落を Google Docs ネイティブ箇条書きに変換（`createParagraphBullets` → 先頭「・」削除）
4. タイトル行 `株式会社〇〇 〇〇様` を所属/氏名に replaceAllText（本文の後＝index非依存）
5. 再取得して `残存 〇: 0` を検証し URL を表示

- ネットワークは **curl 経由**（gcloud token＋Drive/Docs API）。Python 直 HTTPS は環境により SSL で落ちるため使わない
- `--apply` は**外部の共有 Doc を作る**操作。実行前にユーザー確認を取る
- 既存 Doc を直接埋めるなら `--from-template` の代わりに `--doc <DOC_ID>`

### 4. 確認

- スクリプトが出す `残存 〇: 0` と URL を確認。0 でなければ未反映あり
- Doc を開いて見出し・箇条書きの体裁を目視。`background` が会話の選定理由を反映しているか確認
- 箇条書きがネイティブのバレットリストになっているか（「・」がテキストとして残っていないか）確認

## Exit Criteria（終了条件）

- [ ] `background` / `points` に**この会話の選定議論**（接点・なぜこの方か・聞きたい論点）が反映されている
- [ ] `--apply` 後の検証で `残存 〇: 0`（タイトルの所属/氏名＋5空欄すべて）
- [ ] 当事者性が進行形・役割裏取りで書かれ「実装し切った」等の過剰な断定がない
- [ ] 視聴ターゲットが企業規模＋職種で具体化されている

## 既知の落とし穴

- **会話の選定理由を入れ忘れて定型文になる**のが最大の失敗。`background`/`points` は会話起点で書く
- リサーチノートの根拠記事が**解説主体**のとき、それだけで当事者性を主張しない（役割で裏取り）
- **既存Docへ箇条を後から追加する場合**、箇条のネイティブ変換を明示的に実行する。テキスト置換だけでは記号が残る
- `deleteContentRange` で段落末尾 `\n` を消すと段落が結合する。本文 `[start, end-1)` のみ消す（スクリプトが担保）
- タイトル置換を本文 index 編集より先に走らせるとインデックスがずれる。スクリプトは本文→タイトルの順で実行
- gcloud トークンは `auth/drive` スコープが必要（Docs API も drive スコープで通る）
- テンプレが**共有ドライブ**にあると複製に `supportsAllDrives=true`＋親フォルダ指定が必須（無いと `404 File not found`）。`copy_template` で対応済み
