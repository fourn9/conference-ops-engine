# カンファレンス企画の実行フレーム

元の企画フレームから、イベント固有の実例・成果数値・ヒアリング記録を除き、実行規則を整理した公開版。

## 1. 全体フロー

軸定義 → Matrix A（規模×目的）→ Matrix B（職種×目的）→ コアテーマ抽出 → 対象者へのヒアリング → セッション構造 → 登壇候補調査 → 最終判断。

対象者と最終テーマの確定では [insight-gates.md](insight-gates.md) を使う。途中の調査は仮説として進め、決定と区別する。

## 2. 目的軸

| ID | 目的 |
|---|---|
| P1 | 新規サービス立ち上げ |
| P2 | 既存サービスの拡張・スケール |
| P3 | 複数サービスの統合・共通基盤化 |
| P4 | 既存システムの刷新 |
| P5 | 既存サービスへのAI機能追加 |
| P6 | AIを中核にした新設・再構築 |

会社全体の宣言から一律に分類せず、プロダクト単位で判断する。複数フェーズへの該当も許容する。

## 3. Matrix A

企業規模セグメントと目的軸を交差させ、IR・公式発表・中期計画から活動を確認する。技術ブログだけで事業戦略を推定しない。セルごとに活動レベル、根拠、URL、裏取り要否を残す。

◎は注力、○は取り組み、△は限定的、×は確認された活動が少ない状態。根拠がないときは必ず「一次情報なし」と併記する。×を事業が存在しないという断定に使わない。

## 4. Matrix B

### 4.1–4.5 セルの構造

各職種×目的セルで、課題（What）、背景（事実としての状況）、理由（Why仮説）、知りたいこと（セッションで扱う論点）を同じ番号で対応させる。事実と理由仮説を混ぜない。

### 4.6 採否ゲート

| ゲート | 確認すること |
|---|---|
| G1 | 執筆者の職種が特定できる |
| G2 | 本人が関わるプロダクトのフェーズが特定できる |
| G3 | 自社での判断・実装を扱う当事者発信である |
| G4 | 著者・記事の実在と、入力で定めた対象期間を確認できる |
| G5 | その行の職種に適合する |
| G6 | タイトル・サービス名と本文が一致する |
| G7 | キーワード一致だけでなく本文を検証している |

検索→本文を読む→著者・内容種別・該当箇所の引用を記録→採否判定の順で進める。役職・所属を推測で埋めない。隣接職種や概念解説は別枠に残し、該当記事がないセルは空欄を許容する。

Matrix Aの代表企業だけに調査先を限定しない。1記事が複数の論点を裏付ける場合は、その対応を記録する。

## 5. テーマを作る

複数の規模・職種に共通する課題から候補を抽出し、実際に来る対象者の関心に沿って束ねる。機械的なクラスタだけで確定しない。ヒアリングで仮説を修正し、テーマを大・中・小の論点へ分解する。

テーマの性質に応じて粒度を変える。テーマ数とセッション数は同じでなくてよい。小テーマは技術名の羅列ではなく、実行時に生じる判断・制約・比較を表す。

## 6. 登壇候補へ渡す

探索前にテーマ、コアターゲットとの関係、既出候補、採否ルールを確認する。workflowは探索と検証を分ける。G8は本人の実務経験、または本人の独自フレームワークを検証する。Gate Fはテーマごとに入力する判別ルール。

候補の「確定」は根拠を確認した候補という意味で、本人の登壇承諾・契約締結・主催者の最終採用とは別。最終判断は `conference/02-speakers/_selection/` に根拠と `insight_ref` を残す。

## 7. 避ける失敗

- Matrix Aを技術トレンドだけで埋める。
- 事実・背景・仮説・論点を混在させる。
- 企業名や手法名だけでテーマを作る。
- 会社単位で職種・フェーズを決めつける。
- 調査件数を満たすために未検証のURLや人物を補う。
- ヒアリングを経ずに仮説を決定として扱う。
- 全テーマの粒度を機械的に揃える。

実行コードは `.claude/workflows/`、呼び出し手順は対応する `.claude/skills/`、汎用調査プロンプトは [templates/claude-ai-prompt-matrix-b.md](templates/claude-ai-prompt-matrix-b.md) にある。
